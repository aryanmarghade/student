7. STUDENT PROFILE ARCHITECTURE
=============================================================================
The full LinkedIn-style student dossier includes:
- Identity (roll number, avatar, bio, email, branch/year)
- Links (GitHub, LinkedIn, HackerRank, portfolio)
- Projects, Achievements, Certifications, Skills, Hackathons, Documents, Posts.
Note: A profile URL does NOT mean analytics should be generated. External analytics sync is a completely separate system.

=============================================================================
8. POSTS / ACTIVITY
=============================================================================
Posts are created by students and are visible on their profile.
Model: `posts` table includes title, description, category, tags (JSON), and external_link.
Attachments: Supported via `post_attachments` table (image/video/PDF).

=============================================================================
9. MARKS ARCHITECTURE
=============================================================================
Hierarchy: Semester -> Class -> Subject -> Teacher Assignment -> Assessment -> Marks.
- Dynamic Assessment Creation: Teachers define assessments (CA, Mid-Sem, Final) with maximum marks.
- Obtained marks are scoped to the class/subject/semester and the specific assessment.
- Teacher authorization strictly verified before allowing marks entry.
- TEACHER MARKS (internal/ongoing) are strictly distinguished from OFFICIAL ADMIN MARKSHEETS (uploaded as PDFs by admins).

=============================================================================
10. TEACHER ANALYTICS & 11. ANALYTICS VISIBILITY
=============================================================================
Teacher Analytics includes:
- Internal marks, class averages, and performance distributions.
- Linear regression prediction models.
- GitHub, LinkedIn (placeholder), HackerRank (placeholder), Hackathon, and Academic analytics.

Visibility Enforcement:
- Configured by Admins per-teacher in the `teacher_analytics_visibility` PostgreSQL table.
- Flags include: `github_enabled`, `linkedin_enabled`, `hackerrank_enabled`, `hackathon_enabled`, `academic_enabled`.
- Backend filtering is the security boundary. If a teacher's flag is false, the API explicitly omits or denies the data. Frontend hiding is NOT authorization.

13. ADMIN STUDENT PROFILE BUG FIX
=============================================================================
Crucial architecture decision:
The AdminView previously used the teacher-scoped endpoint to fetch student profiles, leading to a 403 Forbidden because Admin is not a Teacher.
Current implementation: AdminView calls `GET /api/admin/students/:studentId/full-profile` which uses admin authorization to bypass the teacher RBAC check and return the full dossier.
Files involved: server/routes/admin-routes.ts, src/lib/api.ts, src/views/AdminView.tsx.

14. DATABASE SCHEMA DOCUMENTATION
=============================================================================
AUTH:
- `users`: id, email, role (admin/teacher/student/placement), password_hash, full_name, is_active, must_reset_password.

ACADEMIC:
- `colleges`, `departments`, `academic_years`, `semesters`.

PROFILE & PORTFOLIO:
- `projects`, `achievements`, `certifications`, `hackathons`: all link to student_id and include `verification_status`.

DOCUMENTS:

- `marksheets`: Official uploaded PDF marksheets with sgpa/cgpa.

COMMUNICATION:
- `notifications`: target_role ('all', 'all_students', 'all_teachers', 'class').
- `notification_reads`, `events`.

ANALYTICS:
- `teacher_analytics_visibility`: Controls admin-configured analytics scopes.
- `student_github_snapshots`: Snapshot history.
- `student_linkedin_snapshots`: Snapshot history.
- `student_hackerrank_snapshots`: Snapshot history.

AUDIT & AI:

15. SNAPSHOT CORRECTION
=============================================================================
Historical snapshots are captured monthly (YYYY-MM).
They use an idempotent upsert: `ON CONFLICT (student_id, snapshot_month) DO UPDATE`.
This means multiple syncs within the same month will overwrite that month's record, ensuring idempotent behavior without generating duplicates.

16. AUTH + RBAC
=============================================================================
- JWT creation in `server/auth.ts`. Payload includes id, email, role, and student/class ID if applicable.
- Passwords hashed via bcryptjs.
- Role Middleware (`requireRole`) checks the decoded token's role array.
- Teacher Scope: `verifyTeacherClassScope()` checks the `teacher_class_assignments` table to ensure a teacher has an active/past assignment to the requested class/subject/semester.
- Admin Authorization: Enforced on all `/api/admin/*` routes.
- Rate Limiting: Configured in `auth.ts` per IP address to protect APIs.

22. ARCHITECTURE DIAGRAMS
=============================================================================
[ OVERALL ARCHITECTURE ]
  React SPA (Vite)  <-- REST API (JWT) -->  Node.js (Express)  <-- pg --> PostgreSQL

[ AUTHENTICATION ]
  Login --> bcrypt compare --> JWT Sign --> Client saves in LocalStorage/Memory
  Client requests --> Bearer Token --> requireAuth Middleware --> Route Handler

[ ADMIN ]
  Admin API --> Has access to all users, classes, analytics visibility, system audits.

[ TEACHER ]
  Teacher API --> Scoped strictly by `teacher_class_assignments`. Can manage marks and view filtered analytics.

[ STUDENT ]
  Student API --> Can view self profile, dossier, transcripts, and notifications.

[ PLACEMENT ]
  Placement API --> Dedicated placement officer scope. Can view aggregated student metrics and dossiers, but not system-wide admin settings.
